Internal infrastructure automation

A design for provisioning and configuring machines with HCP Terraform agents and Red Hat’s managed Ansible Automation Platform, fronted by an Entra-authenticated portal. One guide, two profiles: the company estate on vSphere, and a personal Azure showcase you can later demonstrate to clients.

Estate on-prem VMware, private GitHub Enterprise, CyberArk, Splunk Enterprise, self-hosted workers Showcase your Azure subscription, your Entra tenant, your HCP Terraform org, Azure VMs

Overview

This is a planning document. It does not create an HCP Terraform organisation, an Azure resource, an agent, or application code. The snippets in the IaC blueprint are the shape of a later build, so the design can be reviewed before anyone writes the system.

Recommendation in one paragraph Keep Terraform responsible for the machine and Ansible responsible for what is inside it. Put a thin portal in front of both, and make every integration leave your network as an outbound connection. On the estate, HCP Terraform agents talk to vCenter, and separate AAP execution nodes talk to the guest OS. On the showcase, the same portal runs on Azure and creates Azure VMs, with a small pull-based runner standing in for AAP until you point it at a real controller.

What already exists, and what you would be building

You do not have to invent a developer portal to get a form in front of Terraform. You do have to build one if the thing you want to keep, and later show to clients, is yours.

Build Thin custom portal

A small Python service: catalogue, quota, approval, status. It calls HCP Terraform and AAP. This is the showcase product. The estate can run the same code with a different profile.

HCP Waypoint

HashiCorp’s internal developer platform. Templates wrap no-code Terraform modules. Actions can call HTTP endpoints, including an AAP job, and agent-backed actions can reach a private network. It is included with the commercial HCP story and it is not your product to take to another client.

ServiceNow or Jira as the front door

Right when the company already lives in an ITSM queue. The portal, or a small worker, becomes the fulfilment engine behind a catalog item. Weak as a personal showcase.

Backstage

A general internal developer platform. Worth it when you are publishing many software templates, not when the first outcome is a VM. Heavy for this scope.

VMware Aria Automation

Native vSphere self-service. You have already chosen Terraform as the provisioning standard, including the future Azure landing zone. A second orchestrator for the same VMs splits the operating model.

Use the custom portal. Keep modules no-code-ready so a later Waypoint spike is possible without rewriting them. If the company already mandates ServiceNow for production changes, ServiceNow should open the request and the portal should fulfil it. That is a question further down, and it changes the approval screen, not the agent design.

The two profiles share a contract

One codebase, two deployment profiles. A catalogue item is the contract. It names a pinned Terraform module, an HCP project, an agent pool (or remote execution), a size menu, a quota, an approval rule, and a configuration job. The estate catalogue points at a vSphere module and an AAP workflow. The showcase catalogue points at an Azure module and a pull runner. Neither module tries to pretend vSphere and Azure are the same resource.

Questions

These are the decisions that change the design. Under each one is a working assumption you can overturn. A short reply, by question number, is enough.

1. Where does the HCP Terraform organisation live, and which edition is the estate buying?

Region is chosen at creation. An organisation on app.terraform.io and one on app.eu.terraform.io are different regions. Europe billing is a sales conversation, and feature parity should be confirmed on the Europe plan you are offered. Audit trails, as published in the plan limits, are a Premium feature. Private GitHub Enterprise through an agent is also documented as Premium.

Assume A. Premium, region chosen for data residency

Needed for private VCS and for the audit API the Splunk archive depends on. Confirm Europe if the estate data must stay in the EU.

B. Standard, and keep GitHub reachable by allowlist

Published limits give Standard 10 concurrent agent runs and policy, and they do not give audit logging or private VCS. Enough for throughput of a few dozen builds a day. Not enough for the audit requirement as documented.

C. Free or Essentials for the estate

A pilot only. Free stops at 500 managed resources and 1 concurrent agent run. Essentials raises remote concurrency and still, on the published table, has a single concurrent agent run.

Working assumption A1. Estate Premium. Showcase Free, in your own organisation, until you want the demo to include audit trails.

2. Can HCP Terraform and the AAP control plane reach GitHub Enterprise?

Both SaaS control planes clone Git themselves unless you give them another path. The agent does not automatically solve this. Private VCS is a separate agent feature, and it is documented for Premium. AAP project updates run on the managed control plane, so a private GitHub is also an AAP problem, not only a Terraform problem.

Assume A. GitHub Enterprise stays private

Terraform: a dedicated request-forwarding agent pool, accept ingress only. Ansible: publish collections outbound to the managed Automation Hub from a self-hosted runner. No inbound path to GitHub.

B. Allowlist vendor egress IPs to GitHub Enterprise on 443

Native VCS speculative plans and native AAP projects. Security has to accept HashiCorp and Red Hat source addresses. Drops the private-VCS reason for Premium, not the audit reason.

C. Mirror public-safe repos to GitHub.com

Works with the showcase pattern. Requires a hard rule that those repos contain no secrets, no internal hostnames you care about, and no unpublished code.

D. API-driven uploads only

A runner tars configuration and uploads a configuration version. Works without private VCS. You lose native pull-request plans unless CI does them.

3. What is the system of record for a request and an approval?

Assume A. The portal, with production apply confirmed in HCP

Portal stores the request. Non-production apply uses a team token. Production apply is a human in the HCP UI so the Premium audit event names a person.

B. ServiceNow is the record, portal fulfils

Choose this if production change already has a CAB queue. Do not build a second CAB.

C. A GitHub pull request is the approval

Excellent audit, familiar review, awkward for a developer who should not read Terraform. Fits platform changes better than a VM catalogue.

D. HCP Waypoint, no custom portal

Fast for the estate, and it is not a product you can take to another client. Weak when approval has to be a named manager with a cost centre check.

4. Who is allowed to approve, and what is automatic?

Assume A. Quota auto-approves non-production. Production needs a different person

Requester and approver cannot be the same account. Policy can still reject an approved request. Approval expires after five business days.

B. Every request waits for the platform team

Safest start, and it will not feel like self-service past the first dozen users.

C. Manager approval from Entra, plus platform for production

Needs a reliable manager attribute in Entra. Best enterprise fit if that attribute is clean. Say if it is.

D. Change window plus CAB for production

Only if an ITSM tool already owns the window calendar.

5. How big is one Terraform state?

Assume A. One workspace per VM

Destroy and blast radius stay on one machine. HCP does not cap workspace count. The 30 requests/minute API limit means you must not scan every workspace to learn status.

B. One workspace per application stack

Right when a request is always “app plus database plus disks” and they share a lifecycle. Wrong when people request single VMs.

C. One workspace per team per environment, with for_each

Fewer workspaces. A bad plan can touch every VM the team owns. Rejected for version 1.

D. Stacks, many deployments of one component

HashiCorp’s scale model. Revisit after the portal is boring. Version 1 stays on workspaces because the API and the agent behaviour are the thing you need to learn first.

6. Where do IP addresses and DNS records come from?

A. DHCP, DNS written after boot

Ansible creates the A record once the guest has an address. Simplest non-production path.

B. Infoblox or BlueCat

Terraform reserves the address before create. Use this if the estate already has IPAM and a supported provider.

C. NetBox or phpIPAM

Same shape as B, with a lighter product. Reasonable if nothing else exists.

Assume D. DHCP for version 1, IPAM as a catalogue hook

The catalogue item has a field for the address source. Version 1 only implements DHCP plus an Ansible DNS role against AD DNS. Tell me if production forbids DHCP.

7. What does “login to the VM” mean on day one?

Assume A. Linux SSH, AD integration where the estate already has it, Windows later

Baseline role joins the domain when the catalogue item says so. Local break-glass account is a CyberArk-managed secret, not a password in the template.

B. Windows and Linux in the first release

Doubles the lab: WinRM 5986, sysprep, a second template, a second baseline. Choose this only if the first real consumers are Windows teams.

C. Entra join from day one

Natural on the showcase Azure VMs as a later lesson. Unnatural for on-prem vSphere guests until the estate has that pattern.

8. Which CyberArk interface should automation use?

Assume A. Central Credential Provider (AIM/CCP) over HTTPS with an app identity certificate

Matches AAP’s credential plugin and a small wrapper on the Terraform agent. Certificate per pool, safe per environment.

B. Conjur / Secrets Manager, machine identity

Cleaner if Conjur is already the strategic store. Terraform has a Conjur provider. AAP has a Conjur lookup. Prefer B if both exist and Conjur is the one being invested in.

C. Privilege Cloud

Same consumption patterns as A, different hostname and tenancy. The design does not change; the endpoint does.

D. HCP variable sets as the secret store

Rejected for vCenter. It puts the most powerful password in the SaaS that does not need to hold it. Acceptable for non-network secrets only as a temporary lab shortcut.

9. What is the Splunk topology?

Assume A. Clustered Splunk Enterprise, HEC reachable from an internal collector VLAN

HashiCorp’s Splunk app is documented as unsupported on a clustered Splunk Enterprise deployment. The design uses our own puller into HEC. Indexes: hcp_audit, hcp_runs, aap_audit, portal_audit.

B. Splunk Cloud

The official app can pull audit events if the Splunk side can reach app.terraform.io. HCP’s own log-streaming feature, which pushes to a HEC, is a different product path and its docs reject some Splunk Cloud HEC types, including free-trial endpoints and custom firewalls.

C. Non-clustered lab indexer

You may use the official app. Still keep the run-log puller, because the app takes audit events, not plan and apply stdout.

10. Does a CMDB have to be updated for the VM to count as done?

A. ServiceNow CMDB

Add a step after the baseline. The portal already has the attributes a CI record needs.

B. NetBox

Natural if NetBox is also the IPAM answer.

Assume C. Portal inventory is enough for version 1

A webhook slot exists. No CMDB is in the critical path until you name one.

11. Where does the estate portal run?

Assume A. Two Linux VMs behind an internal load balancer, PostgreSQL beside them

OpenShift is stage 2, so the portal should not wait for it. Do not place the portal on a cluster it is later expected to manage.

B. An existing Kubernetes cluster that is in scope and supported

Fine if platform engineering already runs one and it is not the OpenShift you are postponing.

C. Azure App Service now, talking back to on-prem agents

This is the showcase hosting model. For the estate it puts the workflow engine in Azure before the landing zone is real, and it makes the private path harder.

12. Does egress TLS inspection sit on the path to HashiCorp and Red Hat?

Assume A. Dedicated egress for agents and execution nodes, no TLS intercept

AAP’s pull mesh is mTLS. A proxy that terminates TLS breaks it. HashiCorp’s agent will tolerate an explicit HTTP proxy more readily than the mesh will. Treat inspection bypass as a build blocker, not a tuning item.

B. Everything must use the corporate proxy, and the proxy inspects TLS

The AAP pull model as documented will fail. You would be in the push model, with inbound ports, or you need Red Hat to confirm a supported path. Redesign the network section before building.

13. Are there regulated zones that need their own pools?

Assume A. Three zones: non-production, production, and a reserved name for a regulated zone

Version 1 builds non-production and production pools. A PCI or similar zone gets its own agent pool, execution instance group, CyberArk safe, and catalogue items when you confirm it exists.

B. One flat server network

Fewer moving parts, and a non-production agent that holds production vCenter rights. Rejected.

14. Who owns the VM template, and how often does it change?

Assume A. A separate image process already produces approved vSphere templates

The catalogue references a template name. Terraform clones it. This project does not become the image factory in version 1.

B. This project should build images with Packer

Add it as a later pipeline. Packer can run on the same agent network, in its own pool, so image builds do not share the vCenter role used for everyday clones.

15. Which day-2 actions are in version 1?

Assume A. Create, show status, add a pre-sized data disk, and decommission

Disk and CPU changes are Terraform. Package and account changes are Ansible. Power on/off can wait. Snapshot policy is a tag the backup product already understands, not a workflow we invent.

B. Full lifecycle: resize, snapshot, user add, patch now, restore

A second project. The portal’s action list can grow without changing the agent model.

16. For the personal showcase, how real does Ansible Automation Platform need to be?

Assume A. A pull runner that implements the same job states, and a config switch for a real AAP API

You can demo the pattern without a Red Hat subscription. You must not tell a client the runner is AAP.

B. Buy a personal AAP managed subscription and attach one execution node in Azure

The most honest demo of the mesh, and a real cost. Do this when a client conversation depends on seeing the Red Hat UI.

C. Skip configuration in the demo

You would be showing half the design. Rejected.

17. Which Entra tenant is the showcase allowed to use?

Assume A. A tenant you control that contains no company users or company applications

A dedicated demo tenant is cleaner when you show it to clients. Your personal Azure directory is acceptable if it is truly personal.

B. The company tenant

Out of scope for this project. You said this work is not from the company account.

Catalogue, guardrails, and the module contract

A developer never picks a datastore, a cluster, or a port group. They pick a catalogue item and a size. The platform team maps those to vCenter objects. Quotas live in the portal database so a platform admin can change them without a Terraform release. Every change to quota is itself an audit event.

Suggested hostname pattern: {env}-{os}-{service}-{nn}, for example np-l-payments-04. The portal allocates it. Terraform receives it as an input and does not invent a second name.

Required metadata on every VM, carried as catalogue fields and written into vSphere custom attributes or notes because the vSphere provider’s tag attribute is a set of tag ids, not a free-form map: owner, cost_centre, environment, service, data_class, request_id, managed_by=terraform, backup=standard.

Guardrails, in order:

  1. The form only offers legal combinations. That is the portal.
  2. The module’s variable validation rejects a CPU count the size menu does not contain.
  3. OPA on the plan rejects resource types outside the allowlist, a name that breaks the pattern, and a CPU or memory value above the catalogue ceiling. Free edition can hold one policy set of up to five policies, which is enough for the showcase. The estate uses a VCS-backed policy set, which the docs attach to Standard and Premium.
  4. The vCenter role on the agent account can create in the sandbox or target folder and cannot administer the vCenter.

Pin Terraform itself to an exact version per project, 1.10 or newer at implementation time. Agents download that version from an internal mirror, not from a floating “latest”.

Capacity sketch for purchasing

Agent concurrency is about simultaneous plans, not about how many VMs exist. Three thousand mostly idle workspaces do not need 300 concurrent agents. Standard’s published 10 concurrent agent runs can drain a large nightly drift window if each plan is short, and it is tight if a module upgrade plans hundreds of workspaces during the working day. Premium’s published 300 concurrent agent runs are comfortable. The stronger reasons to buy Premium, on the current docs, are private VCS and audit logging.

Billing is per managed resource per hour, peak in that hour, and a partial hour counts as a whole hour. Workspaces are unlimited on every published plan. A VM plus disks and a NIC is several managed resources; terraform_data and data sources are not. Measure a real plan before you believe a cost model. As an illustration only: if a VM averages 8 managed resources and the published Premium starting rate of $0.99 per resource per month still applies, 3,000 VMs are on the order of 24,000 resources and roughly $24,000 a month at list, before a Flex or enterprise discount. HashiCorp’s product docs also say to contact sales for Standard and Premium. Treat the illustration as a reason to estimate, not as a quote.

AAP on AWS includes two hosted hop nodes and 10 RHEL entitlements for the execution plane, as documented in the service definition. Version 1 needs four execution nodes if you split non-production and production into pairs. That fits in the included entitlements. Size each node at 4 vCPU and 16 GB to start, and watch job queue time.

Personal showcase

Showcase This profile exists so you can learn the pattern on accounts you control, and later show it to a client without ever having pointed the code at the company. It is a real provisioner of Azure VMs. It is not a simulation of vCenter, CyberArk, or Red Hat’s control plane.

Boundary Use a personal Azure subscription and an Entra tenant that contains no company users. Use a separate HCP organisation and a separate GitHub account. Do not copy company hostnames, safe names, or tokens into this repo. When you demo, say which boxes were proved and which are estate-only. That list is at the end of this section.

What the audience sees

  1. You open the portal and sign in with Entra. No local password.
  2. You request “Linux, small, development”. Quota is three VMs so a demo cannot run away.
  3. The portal opens an HCP run. You show the run in HCP, still inside your organisation.
  4. An Ubuntu VM appears in rg-demo-workloads with no public IP.
  5. A runner VM in that VNet picks up a configuration job, SSHs to the guest, and writes /etc/infra-id.
  6. The portal shows the request active, and an Audit page shows the same JSON you would have posted to Splunk.
  7. You destroy it. The VM and the portal row’s status both end. The row remains.

Why remote execution is the default here

Azure Resource Manager is a public API. HCP can reach it. The reason the estate runs agents is vCenter, which HCP cannot reach. Teaching those as the same requirement would be wrong. The showcase default is remote execution with workload identity:

  • One Entra app registration for the portal, confidential client, authorization code with PKCE, app roles Requester and Approver.
  • A second app registration demo-hcp-azure with a federated credential whose subject matches the showcase HCP organisation and project, not one credential per VM workspace. Entra limits how many federated credentials an app can hold, and you will create many workspaces.
  • Workspace environment variables turn on the Azure dynamic provider credentials. No client secret in HCP, in Git, or in the portal.

An optional agent on a small Azure VM, pool showcase-agent, is a catalogue switch. Use it for one request during a demo so you can show the poll in the agent log. Leave the default on remote so a client sees the choice was deliberate.

The runner is not AAP

App Service should not SSH to guests. Guests have no public IP. The runner sits in the VNet, holds an SSH key from Key Vault via its own managed identity, and polls the portal for configuration jobs. That pull is the teaching analogue of an execution node pulling from a hop node. The portal code calls a ConfigRunner interface. The showcase implementation writes a job row. The estate implementation calls the AAP launch API. Swapping them is configuration.

If you later buy AAP yourself, put one execution node in this VNet, peer it to the hosted hop nodes, and switch the profile. Do not keep the homemade runner in that demo, or you will show two orchestrators.

Guardrails you can actually show on Free

The published policy note says Free includes one policy set of up to five policies. The comparison table paints policy as a Standard feature. Believe the more specific note, and recheck on the org. Put five rules in the showcase set: allowed resource types, location allowlist, no public IP, VM size allowlist, required tags. Portal quota is the control that works even if the free policy UI surprises you.

Free does not include the audit-trail API on either published table. The showcase Audit page is fed by the portal’s own events plus run status it already polled. When you move the showcase org to Premium, point the same collector at the audit API and keep the page as a second view. Until then, do not tell a client you shipped HCP audit logs.

How the two agents work together

They are both required on the estate, and they are not two copies of the same idea. HCP Terraform agents change infrastructure through APIs such as vCenter. AAP execution nodes change the operating system through SSH or WinRM. Red Hat’s managed control plane does not reach into vCenter for you, and the Terraform agent does not become an Ansible controller.

HCP Terraform agent

  • Polls app.terraform.io outbound on TCP 443. No inbound port.
  • Runs Terraform for workspaces assigned to its pool.
  • On the estate it must reach vCenter and CyberArk.
  • A separate pool reaches GitHub Enterprise and must not hold vCenter credentials.
  • HashiCorp documents request forwarding as something to isolate from user code. The ingress pool accepts ingress and does not accept plan or apply.

AAP execution node

  • Red Hat runs the controller in their AWS account. You run the execution plane.
  • The service includes two hosted hop nodes. In the pull model, your execution node opens a mutual-TLS websocket to a hop node on TCP 443.
  • A proxy that terminates TLS breaks that mesh. This is documented.
  • Hop nodes route. They do not run playbooks. Test jobs on the controller are the exception Red Hat keeps for the service itself. Your jobs run on your nodes.
  • The node must reach guest SSH 22 and, later, WinRM 5986, plus CyberArk and your DNS.

The handoff

Terraform finishing a VM is not the signal to configure it from inside Terraform. A second apply would re-run a local provisioner, destroy would be confused with “unconfigure”, and the vCenter credential and the root-on-every-guest credential would meet on one host. The portal holds the handoff.

  1. Terraform outputs are the contract: hostname, IP, and request_id. The portal reads outputs, not the state file.
  2. The portal adds or updates one AAP inventory host and launches one workflow job template, limited to that host, targeted at the instance group for that environment.
  3. The controller accepts the launch on its public API. Your portal calls that API outbound. The controller does not connect inbound to the portal.
  4. The execution node, which is already pulling, runs the job. If the job fails, the VM stays, the portal status is config_failed, and the retry button launches Ansible again.

There is an Ansible provider for Terraform and an aap_job resource that can launch a job at the end of apply. It is a reasonable looking shortcut and it is the wrong default here. Keep it as a documented rejection unless you later have no portal at all, in which case Waypoint actions or a run task are still cleaner than a provisioner.

Could they be the same virtual machine?

In a one-node lab, yes. In the estate, no. The apply agent’s vCenter account can create machines. The execution node’s SSH path can become root on the machines that already exist. One compromised host should not get both. Give them different subnets or at least different service accounts, different CyberArk safes, and different admin groups. The ingress agents are a third set, because request forwarding can see tokens HCP asks the agent to present to GitHub.

Identity, secrets, and Splunk

Two different logins

Entra is the identity provider for people. Every product that has a screen gets its own enterprise application and its own SAML or OIDC trust. A user who has signed in to the portal can open a deep link to a run, a job, or a Splunk search and land there without typing a password, because that product also trusts Entra and the browser already has a session. The portal does not forward its access token to HCP, AAP, vCenter, or Splunk. Those products do not accept an Entra token for the portal as a credential.

Automation is a second population. The portal’s team token, the agent tokens, the AAP OAuth token, and the vCenter account are machine identities. They are stored in CyberArk on the estate and in Key Vault on the showcase. They are not the developer’s session. A person leaving the company must not take provisioning with them, and an approval must still name the human who asked.

Portal roles

Use Entra app roles rather than a raw group claim. Large estates hit group overage, and roles stay stable when group names change.

  • Requester can submit and see their own requests.
  • NonprodApprover can approve non-production exceptions over quota.
  • ProdApprover can approve the portal step for production. They also have an HCP account in prod-approvers, because the apply click happens there.
  • PlatformAdmin manages catalogue items and quotas.
  • Auditor can read every request and cannot approve or launch.

The portal refuses a production approval where the approver’s object id equals the requester’s object id.

Break-glass

Turn on “SSO required” in HCP only after two break-glass owner accounts exist, their passwords or keys sit in a CyberArk safe with dual control, and you have signed in with one. Test that path once a year. The same pattern applies to AAP and to the portal’s local emergency admin, which should be disabled in normal configuration and recorded loudly when enabled. Agent token rotation overlaps: create a new token, store it, restart one agent, restart the rest, revoke the old token. HCP allows more than one token on a pool so you do not have to take the pool down to rotate.

Where the vCenter password lives

On the apply agent, a systemd timer calls CCP with that host’s certificate and writes VSPHERE_USER and VSPHERE_PASSWORD into a root-only environment file, then restarts the agent only when the secret changed. The Terraform provider block is empty and reads those variables. The password is not an HCP variable, so it is not sitting in the SaaS as a workspace secret, and it is not in Git. It will still appear in the agent’s memory during a run, and a badly written output can still leak it into a plan log. Mark every module output explicit and small. The Splunk run-log path redacts lines that look like credentials before they are indexed.

AAP uses the CyberArk credential plugin on the machine credential. The controller stores the CyberArk query, not the SSH password. The execution node resolves it at job time.

Splunk

HCP keeps audit events for 14 days. After that they are gone. Splunk is the archive, so the collector is in the same operational class as the agents: if it is down for more than 14 days, you have a gap you cannot backfill. Alert when the checkpoint is older than 30 minutes.

Audit events and run logs are different objects. An audit event says who applied run run-…. The plan and apply stdout is a log you fetch from the run’s plan and apply log URLs. The official Splunk app pulls the audit API. It is the right tool on Splunk Cloud or on a non-clustered indexer, and HashiCorp documents it as unsupported on a clustered Splunk Enterprise deployment. A 3,000-server estate usually has a cluster. Build one collector.

  • It authenticates to GET /api/v2/organization/audit-trail with the audit-trail token. The organisation is implied by the token. Use since and a checkpoint. Page size up to 1000.
  • It writes those events to index hcp_audit and, in the same pass, updates portal rows when the event refers to a request_id it can see in resource metadata or in a workspace tag it has cached.
  • For runs that reached a terminal state and are not yet archived, it fetches plan and apply logs with a team token that is allowed to read those workspaces, redacts, and writes index hcp_runs. Budget this. A noisy fetcher will spend the 30 requests per minute by itself.
  • It never downloads state.

Also index, from Universal Forwarders on the hosts: agent journals to hcp_agent, execution-node journals beside AAP’s own activity stream in aap_audit, and portal application audit events in portal_audit. A useful search is any index containing a request_id.

On the showcase, the portal writes the same event schema into Postgres and renders it. A setting SPLUNK_HEC_URL forwards the same payload when you have somewhere to send it. HCP’s push-based log streaming is a separate feature aimed at Splunk Cloud HEC endpoints, and its docs exclude free-trial endpoints and endpoints with custom firewalls. The puller is the design that works for on-prem Splunk Enterprise. Use it in both profiles.

Correlation

Put request_id on the portal row, the HCP workspace tag, a Terraform output, the AAP extra var, the guest file /etc/infra-id, and every log event. Without that, Splunk has three products and no story.

Runbook

Two tracks. Track C is the estate and assumes company subscriptions, vCenter, CyberArk, Splunk, and a private GitHub Enterprise. Track D is the showcase on your personal Azure and HCP accounts. Do not mix organisations, tokens, or agent pools between them.

Before either track This runbook is the procedure for a later implementation. Following it creates real infrastructure and real spend. Finish the questions that block purchasing first. On the estate, stop at the first verification that fails. On the showcase, set a budget alert before the first VM.

  6. Status updates come from the collector’s audit pass plus a direct poll of AAP for the one job id you launched. The portal does not list every workspace.

Verify: a user without the Requester role gets a forbidden page. A user with the role can submit. Two clicks do not create two VMs. A platform admin can change quota and the change appears in portal_audit.

C18. End-to-end non-production, then production
  1. Submit a sandbox catalogue request as a normal user. Watch the portal status move, the HCP run, the vCenter task, the AAP job, and a Splunk search on request_id.
  2. Kill the baseline on purpose, for example by pointing DNS at a name you cannot write. Confirm status config_failed and that retry does not clone a second VM.
  3. Fix it, retry, reach active.
  4. Decommission. Confirm the retire path: Ansible retire job if you have one, Terraform destroy, AAP host deleted, DNS removed, portal row kept as destroyed.
  5. Only after that, a production catalogue item in a production sandbox if you have one. The portal stops at “plan ready”. A different person opens the deep link, signs in with Entra, and applies. The audit event’s actor is that person, not the portal team.
  6. Attempt to approve your own production request with a second role on the same account. The portal blocks it.

Verify: each of the searches below returns the same request_id: portal row, HCP run, AAP job, Splunk, and /etc/infra-id on the guest before you destroy it.

C19. Drift, windows, and day-2
  1. If the edition includes health assessments, enable them on production workspaces and route the notification into the collector. If it does not, schedule a plan-only run weekly per production workspace, overnight, never all at the same minute. Apply stays off.
  2. A drift finding opens a portal banner. It does not auto-apply in production.
  3. Day-2 “add data disk” queues a new run on the same workspace with a new variable. It uses the same approval rule as create.
  4. Module upgrades are a platform action: change the pinned version on a catalogue item, then upgrade one workspace, then a batch. There is no floating main.

Verify: a by-hand edit in vCenter shows up as drift and does not get silently reverted at 09:00 on a Tuesday while someone is provisioning.

C20. Game day before you call it live
  1. Reboot one apply agent during a plan. The run fails or is picked up according to HCP’s behaviour; the surviving agent serves the next run. Confirm you understand which of those two you observed and write it down.
  2. Revoke the portal team token and confirm new requests fail closed with a clear error, and existing VMs are untouched.
  3. Block egress from an execution node to the hop node. Jobs queue or fail. Restore egress and confirm the mesh recovers without a reinstall.
  4. Sign in with break-glass and with SSO.
  5. Restore a PostgreSQL backup of the portal to a scratch instance and confirm request history is there. HCP state is still the source of truth for the VM; the portal is the source of truth for who asked.
C21. Leave stage 2 as names only

Projects azure-landing and ocp-nonprod exist and contain no workspaces. No Azure service principal is created “just in case” inside the company tenant as part of this personal project. When the company is ready, the Azure catalogue item gets workload identity and, only if private endpoints require it, a new agent pool. The OpenShift catalogue item gets its own pool and a namespace module. Neither reuses the vSphere module.
